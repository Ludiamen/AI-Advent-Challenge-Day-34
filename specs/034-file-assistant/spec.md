# День 34 — ассистент для работы с файлами проекта: спецификация

Документ отвечает на вопросы «что» и «зачем». Как это строится — в [plan.md](plan.md), по
шагам — в [tasks.md](tasks.md).

## 1. Задание (дословно)

> День 34. Ассистент для работы с файлами проекта
>
> Сделайте ассистента, который активно работает с файлами, а не просто отвечает текстом.
> Через MCP или доступный вам tooling ассистент должен уметь:
> 👉 читать файлы проекта
> 👉 искать информацию по нескольким файлам
> 👉 анализировать содержимое
> 👉 создавать или изменять файлы
>
> Примеры сценариев (реализуйте минимум 2):
> 👉 найти все места, где используется определённый компонент / API
> 👉 обновить документацию на основе изменений в коде
> 👉 сгенерировать новый файл (README / ADR / changelog)
> 👉 проверить соответствие файлов правилам или инвариантам
> 👉 подготовить diff или список изменений
>
> Важно:
> 👉 ассистент сам инициирует работу с файлами
> 👉 вы задаёте задачу на уровне цели, а не “открой файл X”
>
> Минимальный результат:
> 👉 ассистент работает минимум с 2–3 файлами
> 👉 изменения сохраняются или выводятся как diff
> 👉 результат можно воспроизвести повторно
>
> Результат: AI-ассистент, который выполняет реальные операции с файлами проекта.
> Формат: Видео + Код

## 2. Что говорит лекция недели 7

Лекция недели 7 (`Day-31/7-неделя-6-поток-v1-1.md`): у ассистента три группы инструментов —
RAG, MCP и системные (файлы, команды); модель выбирает инструмент по описанию, исполнитель
вызывает его и возвращает результат модели. **Опасные операции (удаление, запись файлов,
git push, конфигурация) проверяются отдельно и выполняются только с согласия пользователя.**
В пайплайне — обработка ошибок, повторы, запасной путь и точка, где подключается человек;
проверка на эталонных примерах и оценка человеком.

## 3. Толкование задания

- **«Активно работает с файлами»** — ассистент получает цель («найди, где отправляются
  уведомления», «обнови справочник по коду», «составь ADR», «проверь правила») и сам решает,
  какие файлы перечислить, где искать, что прочитать и что изменить. Человек не называет
  файлы.
- **«Создавать или изменять»** — по-настоящему: правки ложатся в файлы рабочей копии
  проекта и коммитятся; до этого человек видит их как единый diff и подтверждает.
- **«Минимум 2 сценария»** — владелец выбрал четыре: найти использования, обновить
  документацию по коду, сгенерировать ADR / changelog, проверить правила; «подготовить diff»
  входит во все, где есть правки.
- **«Воспроизвести повторно»** — та же цель на том же коммите проекта даёт тот же набор
  затронутых файлов и находок (контрольный набор × 2 прогона); готовый diff применяется
  заново на чистую копию.

## 4. Что уже есть и чего не хватает

Есть (код Дня 33):
- git-сервер MCP Дня 31 (`git_server.py`) — **только чтение**: `git_ls_files`, `git_grep`,
  `git_show`, `git_diff`, `git_changes`, `git_log`; официальный `filesystem` (npx) — тоже
  только чтение;
- цикл модели с инструментами (День 17, `agent/agent.py`) и граница «читающий вызов — сразу,
  меняющий — заявка с подтверждением человека» (`agent/mcp/toolbox.py`);
- анализ: ассистент разработчика Дня 31 (вопросы о проекте с источниками и цитатами), ревью
  Дня 32 (сверка с «конституцией», находки проверяются кодом);
- `projects.json`: проект `crm` — CRM владельца.

Не хватает:
- **ни одного инструмента записи** — все ассистенты отвечают только текстом;
- ассистента, который по **цели** сам выбирает файлы и действия;
- **diff черновика правок**, подтверждения и записи в проект;
- **воспроизводимого** прогона целей с проверкой результата кодом.

Ограничение: в рабочей копии CRM работает другая сессия (незакоммиченные изменения) — её
трогать нельзя.

## 5. Решения владельца (развилки, 2026-10-16)

| Развилка | Решение |
|---|---|
| проект | **CRM в отдельной копии**: свой клон на закреплённом коммите, ветка ассистента; рабочая копия владельца не трогается |
| инструменты | **свой MCP-сервер `files`**: чтение, поиск по многим файлам, запись и правка — только внутри корня копии |
| запись | **diff → подтверждение → запись** (как заявки Дня 17): отказ ничего не меняет |
| сценарии | все четыре: найти использования, обновить документацию по коду, сгенерировать ADR / changelog, проверить правила / инварианты |
| агент | **цикл с инструментами + проверка кодом** результата |
| интерфейсы | **консоль + веб-чат** (`/files` на `/chat`): ход, diff, «Применить / Отклонить» — веб равен консоли |
| модель | ds-flash по умолчанию, ds-pro — выбором; судья контрольного набора — ds-pro |
| повтор | **закреплённый коммит + контрольные цели** по всем сценариям × 2 прогона, журнал задачи |

## 6. Требования

### 6.1 Функциональные

- **FR-01. Рабочая копия проекта.** Ассистент работает в своём клоне CRM (`git clone
  --local`), закреплённом на коммите (`projects.json`: `база`); у каждой задачи — своя ветка
  от базы. Рабочая копия владельца (`~/Документы/CRM`) не меняется: ни файлы, ни `.git`.
- **FR-02. MCP-сервер `files`** (stdio, SDK `mcp` 2.x), корень — копия проекта. Читающие
  инструменты: список файлов по шаблону, чтение файла (диапазон строк, предел размера),
  поиск по многим файлам (строка или регулярное выражение, с номерами строк), оглавление
  файла (функции и классы Python, заголовки markdown), история git (журнал, diff коммитов).
  Меняющие инструменты: создать файл, заменить фрагмент файла (точное совпадение, одно
  вхождение) — **пишут не в файлы, а в черновик правок задачи**; diff черновика. Пути —
  только внутри корня, без `.git`, `.env*`, секретов, симлинков наружу; пределы размера.
- **FR-03. Ассистент.** Цель на естественном языке → цикл модели с инструментами `files`
  (предел кругов и токенов) → итог: краткий отчёт, находки с файлом и строкой, черновик
  правок. Модель сама выбирает файлы; системный промпт описывает проект, правила работы и
  четыре вида целей, но не называет файлы.
- **FR-04. Проверка результата кодом.** Каждая находка — существующий файл, строка и
  дословная цитата (найдена в файле, а если черновик эту строку уже изменил — в базе); находка
  «файл существует» — цитата-путь существующего файла; черновик применяется к базе
  (`git apply --check`); заявленные «прочитанные» файлы действительно читались (журнал
  вызовов); в черновике нет путей вне разрешённых. Непроверенное помечается, а не выдаётся за
  факт. Ошибки черновика, которые модель может исправить сама (не применяется, ADR не по
  шаблону, новые ошибки `tools/sdd.py`), уходят ей обратно — до 3 кругов доработки.
- **FR-05. Подтверждение.** Задача с правками ждёт решения: «Применить» — запись в копию и
  коммит на ветке задачи (сообщение — цель и итог), «Отклонить» — черновик закрывается, файлы
  не меняются. Без подтверждения ни один файл проекта не меняется.
- **FR-06. Сценарии.** (1) Найти все использования компонента / API — список мест с файлом,
  строкой, ролью (определение, вызов, импорт, шаблон, тест, документ); по желанию — отчёт
  файлом. (2) Обновить документацию по коду — найти расхождения кода и документов, правки
  документов diff-ом. (3) Сгенерировать ADR или раздел changelog — новый файл по правилам
  проекта (frontmatter и разделы ADR из `docs/sdd-process.md`, ссылки на коммиты и файлы).
  (4) Проверить правила / инварианты — сверка файлов с `docs/constitution.json` и
  соглашениями SDD, нарушения с цитатами и правки.
- **FR-07. Консоль.** `cli.py --файлы-цель "цель"` (ход по шагам, отчёт, diff; ключ `--файлы`
  занят с Дня 11 — «где лежит каждый слой памяти»), `--файлы-база ССЫЛКА`, `--файлы-задачи`,
  `--файлы-показать ID`, `--файлы-применить ID`, `--файлы-отклонить ID`, `--файлы-повторить
  ID`, `--файлы-случаи`, `--файлы-метрики`; модель и проект — общими ключами.
- **FR-08. Веб-чат.** На `/chat` команда `/files цель` (`/files --база ССЫЛКА цель` — другая
  ветка копии): ход по этапам (какие файлы смотрит),
  карточка итога — находки, diff с подсветкой, «Применить» / «Отклонить»; после перезагрузки
  — на месте. Веб равен консоли.
- **FR-09. Журнал задачи и повтор.** Задача хранит цель, проект, базовый коммит, модель,
  вызовы инструментов (без содержимого файлов сверх пределов), находки, черновик, решение
  человека, коммит. «Повторить» — та же цель на той же базе в новой задаче, сравнение
  затронутых файлов и находок с прежней.
- **FR-10. Метрики.** На задачу — строка без текстов: время, круги, вызовы по инструментам,
  файлов прочитано / изменено, токены, стоимость, итог (правки / только отчёт / ошибка),
  решение человека.
- **FR-11. Сбои.** Облако не ответило — повтор, затем «не выполнено» с причиной (черновик не
  создаётся); инструмент вернул ошибку — модель видит её и может исправиться; предел кругов —
  итог по собранному с пометкой «не завершено».

### 6.2 Нефункциональные

- **NFR-01. Безопасность записи.** Меняющие операции — только в черновик и только после
  подтверждения в файлы; запись вне корня, в `.git`, `.env*`, удаление файлов — невозможны по
  построению (нет инструмента), а не по просьбе модели.
- **NFR-02. Рабочая копия владельца не тронута** — проверяется до и после прогона (статус и
  HEAD).
- **NFR-03. Время.** Цель на ds-flash — до 3 мин (цель 90 с) на копии CRM (~1 800 файлов).
- **NFR-04. Деньги.** Цель — центы на ds-flash ($0,02–0,18); контрольный набор × 2 с судьёй —
  до $1,5 (ворота 1: $1,2–1,35).
- **NFR-05. ПД и секреты.** В журнал, метрики и ответы не попадают значения секретов; ПД
  маскируются, как в Днях 31–33.

## 7. Критерии приёмки

- **SC-01.** Ассистент по цели сам работает минимум с 2–3 файлами — прочитанные (журнал
  вызовов) и файлы подтверждённых кодом находок, — человек файлов не называет — на каждой
  цели контрольного набора.
- **SC-02.** «Найти использования»: полнота по файлам против `git grep -w` по идентификатору —
  ≥ 90 %, выдуманных мест 0 (неподтверждённая находка — только в файле, где имя есть: неточная
  цитата, а не выдумка).
- **SC-03.** «Обновить документацию»: на посеянном расхождении кода и документа черновик
  меняет нужный документ, называет расхождение, применяется к базе.
- **SC-04.** «ADR / changelog»: новый файл проходит проверку формата проекта
  (`tools/sdd.py проверить` в копии — без новых ошибок), ссылается на существующие файлы и
  коммиты.
- **SC-05.** «Проверить правила»: посеянные нарушения найдены — ≥ 4 из 5, ложных — не
  больше 1; правки — diff.
- **SC-06.** Без подтверждения файлы копии не меняются; после «Отклонить» — тоже; рабочая
  копия владельца не меняется никогда (NFR-02).
- **SC-07.** Контрольный набор (≥ 10 целей по 4 сценариям) × 2 прогона ds-flash: в каждом
  прогоне ≥ 80 % целей верны (код + судья ds-pro; в целях, кроме «использований», подтверждено
  ≥ 80 % находок), затронутые файлы совпадают между прогонами (Жаккар ≥ 0,8) на ≥ 80 % целей —
  изменённые файлы, у отчётов — места из эталона; «Повторить» и повторное применение diff —
  работают.
- **SC-08.** Консоль и `/files` в вебе дают одно и то же; браузерная проверка — без ошибок JS.
- **SC-09.** `run_tests.py` зелёный; `check_files.py` — провалов 0; `check_cli.py` часть 34 —
  без расхождений; видео — только окно браузера, кадры проверены.

## 9. Конституция дня

1. Запись в файлы проекта — только после подтверждения человеком; черновик — по умолчанию.
2. Рабочая копия владельца CRM неприкосновенна: ассистент работает в своём клоне.
3. Никаких инструментов удаления, выполнения команд, push — их нет у модели.
4. Находка без файла, строки и найденной цитаты — не находка.
5. Секреты и `.env*` не читаются и не пишутся; ПД маскируются в журналах и ответах.
6. Контрольный набор и проверки — на закреплённом коммите: результат воспроизводим.

## 10. Вне рамок

- Выполнение команд и тестов проекта моделью (системные команды) — только чтение и правки
  файлов; проверки (`tools/sdd.py`, `git apply`) запускает код, а не модель.
- Субагенты и параллельные исполнители — один цикл на цель.
- Push и PR в репозиторий CRM — ветка ассистента остаётся в клоне.
